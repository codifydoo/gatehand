How it works

One issue, from the label to the merge. Every step is a GitHub Actions job in your own repository, and only one of them runs a model.

From an issue to a merged PR

  1. You queue an issue

    Someone with write access labels it agent:ready, or files it with the "Agent task" template. It is taken only with an acceptance section (Done when, Acceptance and the like), and not while it carries size: L, agent:hold or question.

  2. Preflight no model

    Stops unless the agents are enabled, the run is on the agent-runner ref, the breaker is closed, and today's runs and open agent PRs are under their caps. Then it picks the highest-priority, oldest eligible issue, locks it, and reads it once: title, body, and only comments by people with write access, framed as untrusted data.

  3. Code the model

    Runs your system, toolchain and dependencies actions, drops passwordless sudo, then the /agent-implement command. The model edits, tests and commits on a local branch. Its GitHub token reads repository contents only; it cannot push, comment or label.

  4. Publish no model

    A fresh checkout of the default branch takes the agent's commits from a git bundle and validates them: commit shape, bot authorship, no closing keywords, Refs #N, size caps, protected paths. Then it pushes the branch and opens the PR. What the coder noticed but left alone is filed as agent:candidate issues, for you to queue or close.

  5. CI and the Claude review

    The PR goes through your CI and the Claude review like any other. The review's model has no tool that writes; a separate job that runs no model posts its verdict.

  6. The fixer, if needed

    When CI fails or the review asks for changes, the fixer fixes its own PR: at most maxCiFixes times for CI and maxReviewFixes times for a review. After that it is a person's turn.

  7. The merge gate no model

    Merges only when, on the PR's current head, everything holds: the agents are on and no breaker is tripped; the PR is the bot's, open, mergeable, and not held, blocked or being fixed, and no one without write access lifted a hold, reopened it or re-added agent:pr; every required check and agent pr guard passed; the newest review verdict is Approve and newer than the head; no changed file is protected; and the head contains the default branch's tip. It merges with a merge commit pinned to that head, never --admin. With auto-merge off, it only reports what it would do.

  8. You close the issue

    The issue becomes agent:done-pending-deploy. Close it yourself once the change is live.

The workflows

The logic is in .github/scripts/agent-*.sh: deterministic shell scripts that run without a model. State lives in GitHub itself: labels, HTML-comment markers in the bot's comments, and JSON rows on the agent-ledger branch.

What you own, what the package owns

.github/agents/ holds your settings, created once and never overwritten:

FileWhat it is
policy.jsonLimits (runs per day, open PRs, attempts), models, schedules, runners, extra tools, required checks
project.mdYour standing rules and the check commands per area; the agents read it every run
protected-paths.txtPaths an agent PR needs a person's label for, and ! paths it may never touch
system/, toolchain/, dependencies/Composite actions that set up the agent's job like your CI
hooks/lib.shOptional: extra PR-guard rules, inbox request kinds, digest sections

Everything else (the workflows, the scripts, the Claude commands) is rendered by the package and recorded with hashes in .github/agents/install.lock.json. /gatehand:update re-renders them, and refuses to overwrite a file you edited by hand: that change belongs in one of the files above.

The full runbook is also installed into your repository, as .github/agents/README.md.
